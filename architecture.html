What stays exactly the same

✓
Server is the only place a permission is decided
The API re-runs the same _can_user_act / STATUS_ROLE_MAP logic Admin uses today on every write. The UI reflects a role; it never grants one.
✓
City-scoped visibility
Every list and detail query stays filtered by the requesting user's assigned cities — the same scoping Admin applies, moved unchanged into the API querysets.
✓
Media stays direct-to-GCS, signed and path-validated
Photos, videos and documents keep using the existing short-lived signed-URL flow — the frontend just renders it, it doesn't touch how files move.
✓
One record per stage, unchanged
HunterSubmission → BDESubmission → SiteEvaluation → BDMReview → NegotiationRound → CXOReview → ICDecision stay the single source of truth; the UI is a new way to read and write them, not a new data model.
✓
SLA timers, emails and push notifications
Fire from the same signals as today — a stage transition made through the new UI looks identical to one made through Admin, downstream.

Security posture

Auth & session
Reuse the Django session cookie the Admin already issues — same login, same CSRF-protected write path. No JWT, no second credential store, nothing new to secure.
Authorization
Every API mutation re-validates role + acting-stage + city, exactly like the admin formset checks today. A hidden button in the UI is a courtesy, not a control.
Media upload
Signed PUT URLs stay 15-minute, extension + content-type checked, path-regex validated on the model side — identical to the current flow.
New hardening
Rate-limit the signed-URL and auth endpoints (the Admin's session throttling doesn't cover a public API surface) and add structured audit logging on every stage-transition write.
